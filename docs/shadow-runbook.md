# V2 shadow runbook

Status: proposed operator procedure. This document and the local harness authorize no archive-machine command, writer pause, copy, content transfer, Archive admission, or shadow start. Each real operation needs the exact host, path, command, and expected effect reviewed and approved immediately before it runs.

The purpose is to compare a disposable copy with its frozen source and keep a separate report of what Archive can currently account for. V2 supplies source evidence; Archive decides meaning (ADR 0015, ADR 0035). No comparison in this procedure assigns Archive identities or claims.

## Stages

1. **Prepare locally.** Run the synthetic harness below. Identify the exact archive machine, source root, disposable destination, snapshot method, rollback path, and responsible operator in the operation review. For this deployment, the new Archive root must be selected under `/home` on Btrfs so its Git store, records, contracts, and annex content remain within that root. The harness takes only report files or generates temporary synthetic trees; it has no real host or data paths.
2. **Records checkpoint complete.** The first records-root copy is complete. It copied only the V2 records root to an isolated disposable path; no original content bytes moved and no persistent Door command ran against production. The path and digest comparison matched. Source coverage includes one small schema-less file whose route remains unresolved. Do not repeat this copy as part of review.
3. **Content checkpoint complete.** The immutable originals copy, made with `cp -a --reflink=always` from a read-only Btrfs snapshot, matched in file count and bytes. Its checkpoint snapshots have been deleted. The observed comparison establishes byte equality for that copy only; it does not establish power-loss durability, durable content admission, or INV-5. Do not recopy originals as part of review.
4. **Review both checkpoints.** A person reviews both source/copy comparisons, the records census summaries, the separate disposable Archive inventory counts, available snapshot identifiers, and the schema-less file. Record the result with [`shadow/review.py`](../shadow/review.py). Review complete: on 2026-10-14 the operator accepted a record validated as `reviewed` against comparisons re-run from the retained reports. The 2026-10-07 census predated the legacy-citation fix, so both censuses were regenerated by reading only the disposable records copy, bound to the source and copy manifests respectively; the operator accepted that substitution. The record is kept with the reports outside both archives. Accepting the checkpoints does not start the shadow period.
5. **Read-only shadow period and refreshes.** The period starts only after review of both checkpoints and a separate approval to start it. Daily refresh is a planning cadence, not standing authorization or an unattended schedule. Each refresh needs its own exact operation review and immediate approval before any copy operation. Use a consistent source snapshot; restore every paused unit to its captured prior state. Re-run the relevant manifest and census comparisons. Any changed method, destination, writer inventory, or unexpected source change stops the refresh for review. Started 2026-10-15 with the operator's approval: the semantic shadow admits the V2 audio route into a disposable Archive, and the semantic report reaches every migrated Work's occurrences, selections, and spans through World with no locator or pin mismatches. The same day the shadow was rebuilt on layout `archive/2` and specification 0.0.6 ([ADR 0053](decisions/0053-fanned-out-record-and-content-paths.md)); its semantic report equals the first shadow's in every field but the snapshot and specification, and its migration took about seven minutes. The current start record names the record it replaces, and both are kept with the reports outside the archives. No refresh is scheduled.

The CLI in [`../shadow/compare.py`](../shadow/compare.py) compares the source and disposable-copy reports produced by the existing read-only migration tools. It checks reported relative paths, file sizes, SHA-256 digests, and (for the records phase) the separate census reports. It does not read source bytes or authenticate the reports, and it never verifies migration meaning. The reports must be generated reproducibly from the reviewed frozen roots; matching report contents alone do not prove the copy or a claim route.

For a deterministic PAX bundle, [`../migration/v2_lookup.py`](../migration/v2_lookup.py)
opens the candidate through `open_verified_bundle(path)`. Opening verifies the
complete bundle by streaming its members; each later `lookup(locator)` seeks
to the manifest's exact member path and byte offset, checks the record digest,
and returns the exact source bytes with the verified locator metadata. Keep the
returned handle open to look up multiple records without retaining the bundle
in memory. This answers “what exact V2 source bytes does this locator name?”
It does not answer an Archive query, assign Archive identity, or assert an
Archive claim; those meanings remain governed by ADR 0015 and the unresolved
routes reported by the migration census.

The comparator reads at most 64 MiB per report by default. A large V2 census
may require an explicit `--max-report-bytes BYTES` value, capped at 256 MiB per
report. Raising this bound changes only how much of an existing report the
local process will parse; it does not turn an incomplete census into a
complete one. Retain the bounded refusal and report the reason if available
memory is insufficient. The source census may identify a schema-less file or
legacy citation it cannot classify; matching source/copy bytes do not make
those source-coverage gaps disappear.

For records, the schema-less row makes each census incomplete even when the two
manifests and census projections agree. `compare.py` therefore reports
`status: incomplete`, with zero path differences and equal census reports. Its
census summaries identify missing-schema counts and relative source paths. The
review record accepts only that known gap: missing-schema diagnostics must be
the sole census incompleteness, and every named file must have the same size
and digest in both manifests. Other incomplete diagnostics or any inventory
mismatch block acceptance.

## Before the records-root copy

1. Confirm the archive machine's identity and both exact source roots using trusted operator configuration. The records root and immutable originals root are separate roots on separate ext4/Btrfs filesystems; establish which filesystem contains each. Neither source root is a Git or git-annex repository. For this first checkpoint, the copy includes only the records root. The immutable originals root is out of scope until the content checkpoint receives separate approval.
2. Inventory all scheduled and indirect writers before choosing a pause set. Put the exact unit filenames and source paths in the operation review attached to the approval. For each unit, inspect its schedule, executable, arguments, working directory, and children; determine whether it can write the records root, the immutable originals root, or derived inputs to either. Also inspect other timers, services, user jobs, hooks, and manually launched jobs. Classify every item as direct writer, indirect writer, read-only/consumer, or unresolved, and cite the evidence. Do not assume the short list of known units is exhaustive. An unresolved writer prevents a consistent checkpoint.
3. Confirm the disposable destination is isolated, empty, has enough space, and cannot be mistaken for either source root or a production Archive. Supply canonical paths with no symlink in any parent component; both scanners refuse linked root ancestry. Put exact source and destination paths, snapshot method, copy command, bounded pause window, and rollback destination in the immediate operation review.
4. Pause only the inventoried writers required by the reviewed snapshot method. Record each unit's prior state and verify no relevant invocation is still running. Obtain an independently verified snapshot identifier or source manifest for the records root. The source-manifest tool detects many changes during scanning but does not provide an atomic snapshot; the source must remain frozen or be covered by a separately verified filesystem snapshot.
5. Copy only the records root using the reviewed method. Capture the exact command, exit status, source and destination snapshot identifiers, file counts, byte totals, and errors. Verify the destination manifest before restoring every paused unit to its captured prior state. Confirm the observed state matches the capture. If the copy cannot complete within the agreed window, restore prior states, discard the incomplete destination, and schedule a new separately approved attempt.
6. Before any read against the copy, verify all copied data and working stores are inside the approved disposable destination. Check that no symlink, mount, remote, hook, credential, or configuration resolves to production. No operation in the records checkpoint may write to a source root or production Archive.

## Records checkpoint reports

Build a source manifest and census for both the records root and its disposable copy, from the same frozen snapshot on each side. Keep report files outside both roots. The exact paths must be supplied by the operator in the approved invocation:

```sh
python3 -m migration.source_manifest "$RECORDS_ROOT" > "$REPORT_DIR/source-manifest.json"
python3 -m migration.census "$RECORDS_ROOT" --source-manifest "$REPORT_DIR/source-manifest.json" > "$REPORT_DIR/source-census.json"
python3 -m migration.source_manifest "$RECORDS_COPY" > "$REPORT_DIR/copy-manifest.json"
python3 -m migration.census "$RECORDS_COPY" --source-manifest "$REPORT_DIR/copy-manifest.json" > "$REPORT_DIR/copy-census.json"
python3 shadow/compare.py --phase records \
  --source-manifest "$REPORT_DIR/source-manifest.json" \
  --source-census "$REPORT_DIR/source-census.json" \
  --copy-manifest "$REPORT_DIR/copy-manifest.json" \
  --copy-census "$REPORT_DIR/copy-census.json"
```

The manifest comparison checks reported relative paths, sizes, and SHA-256 values. Capture the manifest and census files, command exit codes, and comparator JSON. `migration.census` may exit 1 after writing a report because the schema-less source row is incomplete; inspect the report and retain its exact path and diagnostic. The comparator reports the canonical fingerprint of each supplied manifest, file and schema counts, unresolved route count, unsupported schema count, missing-schema paths, and whether the supplied census reports agree. It never calls those routes translated or authenticates report provenance.

Capture read-only `archive status`, `archive doctor`, and `archive ls` output from a separately identified disposable port instance. Record the Archive Git snapshot, status, archive identifier, specification, context presence, total rows, and shape counts in the checkpoint review record. Keep these counts as their own inventory; the record format and validator do not compare them to V2 counts. An incomplete Archive read blocks acceptance. `archive doctor` also checks every Git object for decay, which Door no longer repeats on each admission ([ADR 0052](decisions/0052-incremental-admission-verification.md)); run it at each refresh, and treat an object-check issue as blocking. When `git count-objects -v` reports many loose objects, run `archive maintenance repack` and then `door verify`, which proves the store again and writes a fresh checkpoint; both take the archive lock. The open identity and contract questions prevent a row-by-row V2-to-Archive identity comparison; matching or mismatching counts do not settle those questions.

A missing root, failed read, incomplete manifest, mismatched path/hash, malformed or unsupported source row, or empty command output is not a zero count and cannot be accepted as a complete checkpoint. The identified schema-less file remains explicitly unresolved even after a successful copy comparison. Archive's supported claim routes and identity rules are listed in the open questions; matching field names do not establish a route.

### Human checkpoint review record

Keep one JSON review record beside the retained checkpoint reports, outside both archives. Use protocol `archive-shadow-review/1` and the closed fields below. The schema-less file row records a relative source path, exact byte count and SHA-256, plus disposition `unresolved_schema-less_source_file`. The digest must match the source and copy manifests. The Archive inventory carries its own Archive Git snapshot and counts; never calculate a V2-to-Archive difference.

The checkpoint summary, with its file counts and bytes, is kept with the
reports outside the repository. One small records file has no schema and
remains unresolved. The snapshots were later deleted. The source and copy manifest
reports and the schema-less path and digest are not in this repository. A
separate local disposable Archive baseline is available, with status `ok` and
two records (one entity and one claim). Reverify its snapshot and counts before
using them in a review record; its transient identifiers are intentionally not
copied into this template. The JSON below is therefore a **hold template**, not
a completed review: fill its report hashes and snapshot references from the
retained checkpoint reports if available, identify and hash the schema-less file,
and record the independently reverified Archive counts. Do not replace unknown
values with zero.

Comparator JSON created before it reported `source_manifest_sha256` and
`copy_manifest_sha256` cannot be used by this validator. Re-run `compare.py`
locally using the retained manifest and census report files to produce bound
comparison JSON; this does not scan a source tree or transfer data. If the
input reports are unavailable, keep the checkpoint review on hold rather than
recreating the checkpoint.

{

Validate the record against both retained comparator results and all four
source/copy manifest reports:

```sh
python3 shadow/review.py checkpoint \
  --record "$REPORT_DIR/records-review.json" \
  --records-comparison "$REPORT_DIR/records-comparison.json" \
  --records-source-manifest "$REPORT_DIR/source-manifest.json" \
  --records-copy-manifest "$REPORT_DIR/copy-manifest.json" \
  --content-comparison "$REPORT_DIR/originals-comparison.json" \
  --content-source-manifest "$REPORT_DIR/originals-manifest.json" \
  --content-copy-manifest "$REPORT_DIR/originals-copy-manifest.json"
```

The validator checks both comparator digests, the manifest fingerprints linked
by each comparator to the four supplied reports, checkpoint totals, the records
census, the complete list of schema-less source paths,
the separate Archive counts, and the human's explicit unresolved disposition.
A result of `reviewed` records that decision; it does not start a shadow period
or authorize a refresh.

## Content checkpoint

The immutable originals root is on its own filesystem and was copied in the separate full content checkpoint. The retained human review should include the already-produced source and copy manifests and comparator report. If those reports are no longer available, record that gap and keep the checkpoint review on hold; do not recreate the copy just to recover reports. The comparison command used for the existing reports was:

```sh
python3 shadow/compare.py --phase content \
  --source-manifest "$REPORT_DIR/originals-manifest.json" \
  --copy-manifest "$REPORT_DIR/originals-copy-manifest.json"
```

The source-manifest tool rejects symlinks, special files, unreadable inputs, and changes observed during scanning; it requires a frozen source and is not an atomic snapshot mechanism. A successful content comparison establishes only that the listed source and destination files had matching paths, sizes, and SHA-256 values during those scans. It does not prove Archive content admission, git-annex no-op behavior, or power-loss durability.

## Refresh and retained report

Daily refresh is a planning cadence. Each refresh is a separate operation requiring immediate approval; no unattended daily job is authorized. Before approval, write one `archive-shadow-operation-review/1` record with exact source and disposable destination paths, host, filesystem and snapshot method, literal copy command, expected effect, full writer inventory and evidence, each writer's prior state and pause/restore actions, rollback path/action, approver, timestamp, and scope limited to one execution. Select `records_refresh`, `content_refresh`, or `full_refresh`; list one source root for a single-root refresh and both for `full_refresh`. A writer class of `unresolved` blocks an `approve` decision. The exact operation and its timestamp remain subject to immediate operator review before execution.

Validate the exact operation review immediately before the proposed operation:

```sh
python3 shadow/review.py operation --record "$REPORT_DIR/refresh-review.json"
```

This is local validation only. It never runs recorded commands, uses SSH,
pauses a writer, or copies data. A `reviewed` result proves only that the closed
record is complete and has no unresolved writer; the operator still needs a
separate immediate approval for that exact one-time operation. No unattended
schedule is authorized. Refresh records include each root's source and
destination snapshot identifiers, start/end time, status, row and byte deltas,
digest failures, unresolved rows, and the captured prior state and restored
state of every paused unit. A changed or incomplete source snapshot, changed
writer inventory, destination outside the approved root, digest mismatch, or
refresh failure freezes the shadow at the last verified snapshot and requires
another review.

Keep these operational reports outside both archives. They are not evidence unless separately admitted through Door. The entire runbook remains a proposal until the exact real operation is reviewed and approved.

## Scratch archives

A scratch archive is a writable copy of the shadow for testing real commits
through a relay ([ADR 0061](decisions/0061-scratch-archives.md)). The operator
has given a **standing approval** for exactly these acts on the archive
machine: a read-only Btrfs snapshot of the source archive, and creating,
resetting, or deleting scratch copies with [`../shadow/scratch.py`](../shadow/scratch.py).
Every other command against the shadow or the real archive, including a
World refresh, a Door command, or making the source a subvolume, still needs
its own approval.

```sh
shadow/scratch.py create trial --source "$SHADOW/archive" --port 8460 \
  --build "$BUILD" --python "$SHADOW/venv-world/bin/python" \
  --relay-config "$SHADOW/relay.json" --publish
shadow/scratch.py reset trial     # drop the copy and snapshot the source again
shadow/scratch.py delete trial    # stop its services and remove everything it made
shadow/scratch.py list
```

`$BUILD` holds `bin/door` and `bin/archive` from the same release as the
checkout that runs the tool. The source must be its own Btrfs subvolume; the
tool refuses anything else and never writes to the source. The copy is one
writable snapshot, and the tool runs as the shadow's user without root: if
`btrfs subvolume delete` is refused, it empties the copy and removes the
empty subvolume with `rmdir`. The copy's relay
has role `scratch` and commits on; clients commit only where the role is
`scratch` ([ADR 0060](decisions/0060-relay-interface-and-role.md)). A scratch
archive shares the source's archive identifier and is never evidence: nothing
is copied back from it.

## Specification upgrade

Status: proposed. Nothing here is approved. Each run, on a scratch archive,
the shadow, or any later archive, needs its own operation review and the
operator's immediate approval for that one run; the scratch standing approval
above covers making scratch copies, not upgrading one.

The shadow is a 0.0.6 archive. Specification 0.0.7 is additive for it, so it
can adopt 0.0.7 by one `door transition`
([ADR 0068](decisions/0068-specification-upgrade.md)): one commit adds the
upgrade record, `spec/0.0.7/`, and the bundles 0.0.7 adds, and replaces
`archive.json` with the new version. No downgrade exists; the only way back is
the Btrfs snapshot taken before the run.

1. **Review.** Name the archive root, the Door build (it must carry 0.0.7, the
   version in its `spec/VERSION`), the operator person's current revision, and
   the snapshot that is the rollback. Rehearse on a scratch copy first and
   keep its result with the review.
2. **Snapshot.** Take a read-only Btrfs snapshot of the archive and record its
   identifier. Stop writers through the relay and the review application for
   the run; Door's lock serializes the rest.
3. **Proposal.** Write a transition proposal directory with one record: a
   Claim with `spec` `archive/0.0.7`, citing
   `archive.transition/specification_upgrade` version 1 under the digest the
   0.0.7 catalog lists, payload `{"from": "archive/0.0.6", "to":
   "archive/0.0.7"}`, and one `authorizer` reference pinning the current
   revision of the operator's person. Its identity row uses namespace
   `archive.transition/specification_upgrade`; `expected_heads` holds a null
   expectation for the new object and the operator person's current revision.
4. **Dry run.** Run `door transition --proposal <directory> --dry-run` from the
   archive root and keep its JSON. It must predict one revision and write
   nothing.
5. **Run.** Run `door transition --proposal <directory>` once the operator
   approves the dry run's result. A refusal writes nothing; record it and stop.
   An uncertain outcome is answered by sending the identical proposal again: a
   committed upgrade answers as a retry. If Door was killed after the commit,
   that next Door finishes the run under the archive lock: it writes the new
   `archive.json` and `spec/0.0.7/` into the worktree and refreshes the Git
   index to the commit, so no `git read-tree` by hand is needed. A Git index
   that holds a change Door did not make is left as it is, and Door refuses
   the next write until the operator resolves it.
6. **Check.** `git show --name-status HEAD` lists exactly `M archive.json`, the
   three `spec/0.0.7/` documents, the added bundles, and the record. `archive
   status` reports `archive/0.0.7` with no issue, and `archive doctor` passes.
   World's next refresh rebuilds its projection in full, because the
   specification changed; the relay reports the new version from the next
   answer on.
7. **Record.** Keep the review, the snapshot identifier, the dry-run and
   committed JSON, and the checks with the shadow's reports, outside the
   archive. Delete the snapshot only after the operator accepts the result.

## Synthetic harness

From the repository root, these commands create only temporary synthetic trees, use the existing read-only manifest/census tools, and remove the temporary data on exit:

```sh
python3 shadow/compare.py --fixture records
python3 shadow/compare.py --fixture content
python3 shadow/compare.py --fixture mismatch
```

The first two return a JSON `matched` report-pair summary. The records fixture also reports migration as unverified with unresolved route counts. The mismatch fixture must exit 1 and report mismatched files. Every result states that Archive identities were not compared, source bytes were not rechecked by this comparator, claims were not translated, durability was not proven, and INV-5 was not proven. Real report mode accepts only explicitly named regular report files; `review.py` accepts only local review/report files. Neither tool opens a source root, invokes SSH, mutates an archive, pauses a writer, executes a recorded command, or transfers content.
